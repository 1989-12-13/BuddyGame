# 《120 调度台》并发值班玩法设计方案 v1

> 本文档是玩法重构的设计基线，用于拍板与迭代。核心改动：**从「5 通线性闯关」改为「并发多线值班」**。
> 状态：待评审（评审通过后再进入原型实现）

---

## 0. 设计目标与已锁定决策

### 0.1 要解决的核心问题

| 现有问题（来自试玩反馈） | 本方案的解法 |
|---|---|
| 派车后干等、想关掉游戏 | 并发线路：永远有下一通在响铃 |
| 五通硬编码、枯燥闯关 | 班次化 + 病例池采样 + 卡片变体 |
| NPC 语言不真实、无区分度 | 规则模板对话：事实槽 × 人物特质 × 情绪 |
| 安抚是鸡肋、情绪无感知 | 情绪影响信息保真度，可被看见 |
| 车辆周转拖节奏 | 车辆成为稀缺资源，取舍取代等待 |
| 失败没有心情波动 | 班次后果链 + 结局化总结 |

### 0.2 已锁定决策（设计定稿）

**结构层**

1. **整体结构**：把「5 通线性闯关」整体改为「并发多线值班」。
2. **并发程度**：直接上并发，不做单线折中版。
3. **线路 / 车辆**：默认 **3 条线路 / 2 辆车**。
4. **班次时长**：**不硬规定**，由事件队列与线路占用自然决定。
5. **教学首通**：**不做**固定首通，全部事件动态化（新手引导不在本次范围）。

**系统层**

6. **对话生成**：规则模板生成（不接 LLM 实时生成）。
7. **问询形态**：「系统管顺序、玩家管措辞」的对话回合（§6），保留捷径型选项，每回合 2–4 个。
8. **情绪系统**：锦上添花但需适当管理——不影响能否通关，只影响效率与信息质量；**思考时情绪缓慢上升**。
9. **车队**：2–3 辆（默认 2）；"加速周转"已删除。
10. **Perks**：**重做**为「调度专长」。

**范围层**

11. **卡片改造**：首批只改 **5 张高频卡片**。
12. **删除项（已实施）**：路线策略标签 ✅、加速周转 ✅；**低分小游戏不降频** ❌（全部保留）。
13. **交付节奏**：设计定稿后进入阶段 A 实现。

### 0.3 明确不变的部分

- 公益急救科普的定位与免责声明。
- MPDS 5 步标准协议（地址 / 情况 / 联系人 / 目的）——反馈中认定为「帮助」，保留为**系统驱动的骨架**（见 §6）。
- 知识卡 / 公益知识环节（保持现状）。
- 节奏按压、CPR 两类小游戏（反馈中明确认可）。
- 双主题、设计令牌体系、移动端可玩。

## 1. 核心结构：一个班次（Shift）

### 1.1 单位变化

| | 现有 | 新方案 |
|---|---|---|
| 游玩单位 | 一通电话 = 一关 | **一个班次 = 一整块时间轴** |
| 顺序 | 固定串行、可预测 | 并发、动态到达 |
| 结算 | 每通评分 + 5 通累计 | 整班结算（含过程事件） |
| 结束条件 | 打完 5 通 | 班次时间到 / 事件全部收束 |

### 1.2 时间模型

- **不设定固定班次时长**。班次由**事件队列与线路占用情况**自然决定——处理得快就短，处理得慢就长。
- **结束条件**：事件队列耗尽 + 所有线路空闲（在途车辆收束完毕后进入结算）。
- 时钟：沿用现有 `TICK`（1 秒/tick），但**tick 必须推进所有线路**，而非仅当前通话。
- 暂停规则沿用现有设计（暂停 / 设置 / 后台切换 / 弹窗共用同一计时规则）。

### 1.3 班次配置

班次由配置生成，而非硬编码：

```ts
interface ShiftConfig {
  id: string
  lineCount: number             // 电话线路数（默认 3）
  vehicleCount: number          // 救护车数（默认 2）
  incidentQueue: IncidentSpec[] // 本班事件队列（顺序 = 到达顺序）
  difficulty: 'calm' | 'normal' | 'peak'  // 决定到达间隔与并发压力
}
```

- **无固定时长字段**：班次长度 = 事件队列长度 × 玩家处理速度。
- **难度档位**只影响「事件到达间隔」和「并发数量」，不影响单通难度。
- **取消固定教学首通**：所有事件均由队列驱动，第一条也是动态的（新手引导不在本次范围）。

## 2. 三层实体模型（本次重构的关键）

现有状态机只有一个 `currentCall`，无法承载并发。新模型拆成三层：

```
┌──────────────────────────────────────────────────────┐
│  Line（电话线路）× 3         —— 玩家注意力的"槽位"      │
│  ├─ idle      空闲                                     │
│  ├─ ringing   响铃中（有超时）                          │
│  ├─ active    通话中（聚焦或后台）                       │
│  ├─ hold      保持中（未挂断，来电者在等）                │
│  └─ done      本通结束                                  │
└──────────────────────────────────────────────────────┘
                     ↑ 承载
┌──────────────────────────────────────────────────────┐
│  Call（通话实例）             —— 一次来电的全部状态      │
│  ├─ caller: Persona + 情绪 + 配合度                     │
│  ├─ case: 病例事实槽 + 问询进度 + 终端字段               │
│  └─ guidance: 指导进度 / 小游戏结果                      │
└──────────────────────────────────────────────────────┘
                     ↑ 属于
┌──────────────────────────────────────────────────────┐
│  Incident（急救事件）         —— 一次真实事故            │
│  ├─ 初报 Call / 回拨 Call（同一事件可多次来电）           │
│  └─ rescue: Vehicle + 在途状态 + 现场结果                │
└──────────────────────────────────────────────────────┘
```

**为什么要分三层**：

- `Line` 决定"玩家能同时做几件事"（注意力稀缺的来源）。
- `Call` 承载"一通电话里的所有玩法"（复用现有大部分问询/指导逻辑）。
- `Incident` 让"同一事故的多次来电"成为可能（初报慌乱、家属回拨、补充信息），这是叙事与信息质量的关键来源。

## 3. 注意力经济（核心玩法）

**这是本方案真正替代「等待」的机制。**

### 3.1 基本规则

- 玩家**一次只能聚焦一条线路**（聚焦 = 工作台显示该通话的完整信息）。
- 非聚焦线路仍在实时推进：
  - 响铃线路会**超时**。
  - 通话中线路的来电者情绪会**缓慢上升**（被冷落焦虑）。
  - 车辆会上报在途事件。
- 切换线路有**上下文成本**：切换会打断正在播放的语音、需要重新读一遍对话（UI 上做成"未读标记"）。

### 3.2 由此产生的持续决策

玩家的核心问题从"下一步点哪里"变成：

> **"现在这 10 秒，我该花在哪条线路上？"**

每一个选择都有代价：

- 接新来电 → 当前通话的来电者被冷落、情绪上升。
- 继续深挖当前信息 → 另一条线路在响铃、可能错失。
- 做 CPR 指导 → **该线路被锁定**，完全无法分身（见 §8）。

### 3.3 响铃超时的处理（不硬性失败）

响铃超过 `RING_TIMEOUT`（建议 20–25 秒）未接：

- 线路自动转入**留言**：记录一条**模糊信息**（如"地址只说了大致路段"）。
- 该来电者情绪显著上升，并在稍后**回拨**（重新响铃，且开头就带情绪）。
- 结算时计入"响应及时性"扣分。

> 设计意图：惩罚明确但不熔断，避免玩家因一次失手就崩盘；同时"回拨"制造后续压力。

## 4. 线路状态机

```
                 ┌─────────┐
      事件到达 ──▶│ ringing │──接听──▶ active ──派车──▶ (事件进入 enroute)
                 └────┬────┘           │  ▲
              超时未接 │                │  │ 切回
                 ┌────▼────┐   暂挂    │  │
                 │ 留言/回拨│◀──hold ──┘  │
                 └─────────┘             │
                                   指导完成/END_CALL
                                         │
                                      ┌──▼──┐
                                      │ done│──▶ 线路释放，可接入下一通
                                      └─────┘
```

关键新增状态：

- **`hold`（保持）**：玩家主动暂挂当前通话去处理别的线路。来电者在线等待，情绪随时间上升。允许"再接回"。
  - 这是并发玩法下的必要操作，也是制造取舍的核心。
- **`ringing`（响铃）**：有独立倒计时，UI 必须高度可见（声音 + 视觉脉冲）。

## 5. 情绪系统与规则模板对话（治「AI 味」）

### 5.1 情绪定位（按决策：锦上添花但需管理）

| 维度 | 设计 |
|---|---|
| 是否影响通关 | **不**。情绪再高也能问出信息，只是慢、可能出错。 |
| 是否影响信息质量 | **是**。情绪决定回答的保真度。 |
| 是否可感知 | **必须**。语音语调 + 文本措辞 + 视觉指示器。 |
| 是否需管理 | **需要**。放任 → 信息获取效率大幅下降、回拨增多。 |

### 5.2 事实槽（Fact）—— 把写死的台词拆开

每张病例卡片不再写"回答台词"，而是定义**事实槽**，每个槽有三级保真度：

```ts
interface Fact {
  clear: string       // 情绪平稳：准确、完整
  vague: string       // 紧张：模糊、缺失关键细节
  distorted: string   // 恐慌：错误、跑题、自相矛盾
}

interface CaseFacts {
  address: Fact
  chiefComplaint: Fact
  age: Fact
  consciousness: Fact
  breathing: Fact
  // ...按卡片需要扩展
}
```

示例（望江路某事件）：

```ts
address: {
  clear:     '望江路 128 号 3 栋 2 单元，楼下有个红色便利店',
  vague:     '望江路 128 号吧……哪一栋我记不清了',
  distorted: '就那边那个小区啊，你快点来！（未提供门牌）',
}
```

### 5.3 人物特质（Persona）— 已实施

实际落地：`CallerVoice`（`game/types/caller.ts`）+ 33 人特质表（`game/npc/voices.ts`）+ 合成引擎（`game/core/callerVoice.ts`），在 `reducers/askQuestion.ts` 单一出口接入。`relation` 复用 `personas.ts` 既有字段，不再重复定义。

```ts
interface Persona {
  verbosity: 0 | 1 | 2        // 沉默寡言 / 正常 / 话痨
  rationality: 0 | 1 | 2      // 情绪化 / 正常 / 理性
  medicalLiteracy: 0 | 1 | 2  // 无常识 / 一般 / 有医疗背景
  relation: 'self' | 'spouse' | 'child' | 'parent' | 'neighbor' | 'stranger' | 'bystander'
}
```

特质决定**措辞包装**：

- `verbosity` → 话痨型会在答案前后加铺垫、跑题；沉默型会截断、只给关键词。
- `rationality` → 理性型能配合"是不是/有没有"的封闭式提问；情绪化型需要安抚才给准确答案。
- `medicalLiteracy` → 高常识者主动提供关键信息（"他嘴唇发紫"）；低常识者只会说"他不行了"。
- `relation` → 决定情绪基线与可用信息（家属知道病史，路人只知道现场）。

### 5.4 回答合成

```
answer = compose( factVariant, personaWrapper, questionType )
```

- `factVariant`：由当前情绪档位在 `clear / vague / distorted` 中选取。
- `personaWrapper`：按 `verbosity` / `rationality` 加修饰、增删信息。
- `questionType`：封闭式（是否）→ 得到是/否；开放式 → 得到叙述。

**worked example** —— 同一个"地址"问题：

| 人物 | 情绪 | 输出 |
|---|---|---|
| 话痨邻居 · 低常识 | 紧张 | "哎呀就是望江路 128 号那边嘛，我每天去买菜的那个路口拐进去……具体哪栋我真没看清，你快派人来啊" |
| 沉默路人 | 平稳 | "望江路 128 号。" |
| 情绪化家属 | 恐慌 | "就那边那个小区！你们怎么还不来！"（地址缺失） |
| 理性医护人员 | 平稳 | "望江路 128 号 3 栋 2 单元，伤者男性约 60 岁，已失去意识，呼吸存在。" |

→ 同一张卡片，四种完全不同、且**信息量真实不同**的回答。这就是"规则模板"能达到的真实感。

### 5.5 情绪的可感知与可管理（已实施）

**核心因果链：情绪越高 → 回答越失真 → 安抚是唯一能提升信息质量的手段。**

- **机制**：准确信息（`clear`）要求压力 < 25；25–49 得 `partial`；≥50 得 `vague`。
  因此「紧张 / 恐慌 / 失控」的来电者默认拿不到准确地址与体征。
- **解药**：安抚降低压力；压力回落到低于提问时刻后，才出现「复核」选项，重问可得更准信息。
  安抚效果线性递减但**保留下限**（20 / 16 / 12 / 8 / 8 …），替代旧版 `20/(1+次数)` 的收益崩塌
  （旧版第 3 次只剩 6.7，导致「安抚换准确信息」在数值上不成立：失控 85 要压 20 次才到 25）。
- **可感知**：问询面板顶部「信息状态」条逐字段显示质量（清晰 / 基本可用 / 模糊 / 未获取）；
  情绪 ≥50 时给出显式因果提示并指向安抚。
- **自然增长**：长时间未被聚焦、长时间沉默 → 压力上升（并发值班的冷落焦虑）。

> 明确**不做**「理性型不吃安慰」。安抚对所有人有效，区别只在收益与时机。

## 6. 问询：回合制对话选择（Dialogue Turn）

### 6.1 核心改动

把"玩家从问题库里**挑问题**"改为"玩家选一句**要说的话**"。

> **分工原则：系统管顺序，玩家管措辞与时机。**

- 顺序不再由玩家维护——**5 步协议（地址 / 情况 / 联系人 / 目的）作为骨架自动推进**，卡片在其上叠加 MPDS 追问。
- 玩家每回合面对的是 2–4 个"我该说什么"的选项，而不是一张需要自己规划的问询清单。
- 现实依据：真实 MPDS 本身就是决策树，调度员按协议走。这个改动同时**更真实**和**更省认知负担**。

### 6.2 一个回合的循环

```
来电者说一句（规则模板生成，受情绪影响）
        ↓
系统给出 2–4 个「你要说的话」选项
        ↓
玩家选择
        ↓
结算：推进协议进度 + 改变情绪 + 揭示/修正信息
        ↓
（下一个回合）
```

- 每通电话独立维护回合进度（切走再切回不丢）。
- 登记表（Terminal）不再是玩家"填表"，而是回合结果的**自动归档**；玩家只负责确认。
- 线路墙显示各线路的协议完成度（如 3/5）。

### 6.3 选项的四种类型

| 类型 | 作用 | 代价 |
|---|---|---|
| **推进型** | 按 5 步协议问下一个该问的 | 无额外代价，最稳 |
| **安抚型** | 情绪↓、来电者更配合 | **耗时间**、不推进协议 |
| **确认型** | 复核已记录信息，可**修正错误信息** | 耗时间，但能纠错 |
| **捷径型** | 跳过若干步直奔关键信息 | 情绪高时可能得到**错误答案**（高风险高回报） |

### 6.4 选项如何生成

由 **[协议进度 × 未确认事实 × 情绪档位 × Persona 特质]** 规则生成：

- 未确认的事实 → 出现对应"推进型"选项。
- 情绪高于阈值 → 追加"安抚型"选项（`rationality` 低的人更需要它）。
- 存在可疑信息 → 出现"确认型"选项。
- 时间紧张或险情明显 → 出现"捷径型"选项。

### 6.5 ⚠️ 为什么不能做成纯线性

如果每个回合只给一个"继续"按钮，问询会退化成**"点下一步"**，正好叠加本项目原有的批评（"问询最像走流程"）。

因此硬性约束：**每个回合必须保留至少一个真实取舍**，且取舍必须是"效率 vs 情绪"或"快 vs 准"这类有后果的选择。

### 6.6 与情绪系统的联动

- 安抚型 → 情绪↓、时间↑
- 施压/催促型（推进型的激进措辞）→ 信息更快，但情绪↑，后续回答质量下降
- 捷径型 → 情绪低时是神操作，情绪高时是灾难
- **回合内的犹豫成本**：玩家停留思考时，来电者情绪缓慢上升（把"思考时间"也变成资源）

### 6.7 示例（跌倒事件 · 邻居来电 · 情绪「紧张」）

> **来电者**：「哎呀你们快来吧，我家隔壁那个老爷子摔倒了！」

| 选项 | 类型 | 结果 |
|---|---|---|
| 「别急，先告诉我准确地址，我马上派车。」 | 推进·安抚 | 地址以 `clear` 档给出，情绪小幅↓ |
| 「地址！快说地址！」 | 推进·施压 | 地址以 `vague` 档给出（被催急了说不清），情绪↑ |
| 「他现在还有意识吗？」 | 捷径 | 跳过地址先拿到意识信息，但地址未落地，情绪不变 |
| 「您是他的家属吗？」 | 推进 | 正常走协议，无情绪波动 |

→ 玩家不需要"记住 5 步顺序"，但每一个选择都有真实后果。

### 6.8 交叉信息（并发带来的新玩法）— 已实施

**① 同一来电者改口（通话内冲突）**

- `CallEvent` 新增 `type: 'caller_correction'` 与可选的 `correction`（问题 + 选项）。
- `applyCallEvents` 触发时追加一条来电者台词 **+ 一张重新判断卡**（复用 `pendingJudgments`）。
- 样例：`fallsElderlyCard` 的 `falls_consciousness_correction` —— 45 秒时来电者改口「叫他没应了」，
  与先前「有反应」冲突，玩家必须决定是否按最新观察更新并重新确认呼吸。

**② 第二位来电者（跨线路冲突）**

结构性约束：**一个事故只有一个患者**。两条线路各持有独立 `WorldState`、各自一份 `patientStatus`；
若第二位来电者也跑完整救援，就变成两个人同时衰减。因此第二位来电者是一条**核实通话**：

- 不拥有患者（`handleAnswerCall` 对 `isVerification` 不创建 `patientStatus`）、不派车、不指导。
- 场景由初报派生（`core/supplementCall.ts`）：确定性挑选另一位来电者，
  并把**呼吸描述反转为相反结论**，形成真正需要判断的冲突。
- 班次层引入 `ShiftIncident` 关联两条线路；初报**派车后**才可能引来第二通
  （`SUPPLEMENT_DELAY`，且需有空闲线路）。
- 玩家在核实面板三选一：**采纳最新观察 / 维持初报 / 再追问一次**（追问每通限一次）；
  处置结果写入该通登记表，并标记事故已解决。
- 线路墙显示「同一事故 · 有第二通 / 核实通话」，并发下不会漏。

## 7. 车队与在途事件

### 7.1 车辆（2–3 辆，默认 2）

```
available ──派车──▶ enroute ──到达──▶ onscene ──送医──▶ returning ──▶ available
```

- 车辆**不再每通配一辆**，而是全局限量。
- 派车决策 = **"这辆唯一可用的车给谁"**（配合并发线路，形成资源取舍）。
- 取消现有"加速车辆周转"按钮（反馈认定为拖节奏）。
- 车辆比线路少（3 线 / 2 车）→ 注意力与资源双重紧张。

### 7.2 在途事件（替代"干等"）— 已实施

车辆 `enroute` 时按计划触发，需要玩家在**其他线路的间隙**处理：

| 事件 | 玩家决策 | 状态 |
|---|---|---|
| 道路拥堵 / 事故 | 是否改道（沿用现有重规划 UI） | ✅ 已泛化到**所有场景**（原先只对脑卒中生效） |
| 来电者改口 / 信息冲突 | 信哪一条、是否重新确认 | ✅ 已接入（见 §6.8） |
| 现场情况变化 | 是否加派第二辆车 / 升级优先级 | ⬜ 待做 |
| 患者病情恶化 | 调整电话指导内容 | ⬜ 待做 |

**并发下的可见性（关键补充）**：不聚焦的线路不会渲染工作台，在途事件会被静默堆积。
因此线路墙新增「待决策」标记与计数（`lineNeedsDecision` / `pendingDecisionCount`），
让"后台发生的事"重新回到玩家视野内。

> 关键：在途事件**不是等待的填充物，而是主动打断**——它和响铃线路一起争抢玩家的注意力。

### 7.3 路线选择（已实施）

- **删除路线策略标签**（「高架抢时线 / 学校均衡线 / 社区稳妥线」及其优劣摘要）——它们替玩家做了决策。
  - 已从 `RoutePlan` / `RouteTemplate` / `DispatchRecord` 移除 `label` / `summary` / `routeLabel` 字段。
  - 派车对话、改道对话、现场交接清单、复盘文案中的路线命名一并改为中性表述。
  - **保留**：逐段路况文字（畅通 / 车流较大 / 拥堵 / 维修施工 / 学校路段 / 事故占道）、ETA、风险提示。
- 玩家须自己读路况文字判断走哪条路。

## 8. 指导与小游戏

### 8.1 线路锁定机制（并发下的关键取舍）

- 进入电话指导（尤其 CPR / 节奏按压）后，**该线路进入锁定状态**：玩家无法切走，直到指导结束或主动中断。
- 这意味着：**做指导 = 放弃这段时间对其他线路的响应**。
- 由此产生的真实决策："现在这通电话还没到最危险的时候，我要不要现在开始 CPR，还是先接那通响铃？"

> 这是把"小游戏"从"独立环节"变成"资源配置决策"的关键改动。

### 8.2 保留与裁撤

| 小游戏 | 处理 |
|---|---|
| 全部 7 种（RhythmPress / CprGame / QuickChoice / LocationSelect / HoldPressure / PositionDrag / StepOrder） | **全部保留，出场频率不变**（本次不做降频） |

> 唯一与小游戏相关的改动来自 §8.1 的**线路锁定**——那是并发结构带来的必然结果，不是降频。

### 8.3 判断选择题

- 保留（反馈：正常频率、能学到东西）。
- 判断失误扣分从 **-8 降至 -5**，并允许"暂缓判断"（不扣分也不加分），避免玩家"宁可不判断"。

## 9. 评分与结算

### 9.1 从"单通评分"到"班次结算"（已实施）

**复用既有 `EndingScreen`**，不新造结算画面。并发模式原本在收束后是死路（只有一句"班次结束"），
现在接上既有结算。两个必要的适配：

1. **跨线路成绩累积**：线路会被复用，而复用时 `START_SHIFT` 会重置该线路的
   `totalScore` / `callScores` / `activePlaySeconds`——直接读线路会丢掉前面的成绩。
   因此在线路 `active → done` 的瞬间把成绩快照进 `ShiftState.completed`。
2. **未接来电计入**：`shift.missed` 按 0 分追加为一条"接警记录"，让漏接的通话出现在结算里。

```
班次总分 = Σ 各通基础分 + 班次事件奖惩
```

维度（沿用并扩展现有 4+1 维）：

| 维度 | 说明 |
|---|---|
| 响应及时性 | 接听及时、回拨处理、响铃错失 |
| 信息准确 | 地址 / 意识 / 呼吸等关键字段的正确性 |
| 优先级判断 | 并发下"先接哪通、先派哪辆"的正确性 |
| 资源利用 | 车辆调度效率、空驶率 |
| 指导质量 | 保留现有的指导评分 |

### 9.2 结局化总结（治"失败无感"）— 已实施（增量，非重写）

`EndingScreen` 保持原结构（评级 → 总分 → 今晚接警记录 → 结局文案），新增可选区块表达并发独有的信息：

1. **逐通卡片带场景名**：`ShiftSummary.calls / missed` 提供场景标题，卡片上直接写出是哪一通；
   未接来电在卡片上标为「未接 · 场景名」。
2. **未接来电单独成组**：不再只混在卡片里当一个 0 分，单独列出并计数。
3. **同一事故的交叉核实结论**：`ShiftIncident.resolution` 记录采纳 / 维持，
   在「跨线路回顾」里逐条展示。
   - 注意：结论必须记在**事故**上，因为承载它的线路会被释放复用，
     届时 `line.verification` 会被清空（与成绩快照是同一类陷阱）。
4. **跨线路叙事总结**：`ShiftSummary.narrative` 生成一句话，例如
   「你今晚接住 3 通，漏接 1 通，1 起事故收到第二位来电者，采纳最新观察 1 次、维持初报 0 次。」

> 线性模式不受影响：`shiftDetail` 是可选 prop，未传入时界面与行为完全不变。

班末不再只给分数表，而是：

- **"你今晚救了谁 / 错过了谁"** 逐条回顾（含你指导过的患者结果回访）。
- 结果以"回访 / 家属致意 / 新闻播报"等**叙事形式**呈现，而非纯数字。
- 这是唯一能让失败真正产生情绪波动的机制。
